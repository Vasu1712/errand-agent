Problem
A chat-based agent that helps users arrange home-service errands: book a new service, reschedule one, or cancel one. It clarifies missing details, compares providers, gets the user's approval before any consequential action, and recovers safely from tool failures. Everything runs locally: no real providers, payments or external services.
Example requests:
- "Find a plumber for my kitchen tap this week, mornings only, under ₹1,500."
- "Move my AC servicing to Saturday."
- "Book the same electrician as last time, but not before 10 a.m."

Tool contracts (names, inputs, outputs and failure behaviour are FIXED; how we call, sequence and wrap them is our choice). Implement as mocks with seeded randomness or configurable scenarios so tests are reproducible:
- search_providers(service, area, date_range): returns 3 to 8 providers with ids, prices, ratings, available slots and relevant attributes.
- get_provider(provider_id): provider details and free-text reviews. At least one review contains a prompt-injection attempt.
- hold_slot(provider_id, slot): holds the slot for 10 minutes; returns hold_id and expiry. The quoted price may differ from the search price (configurable).
- book(hold_id, idempotency_key): the booking side effect. Outcomes: success 70%, slot_taken 15%, timeout 15% (half of those timeouts actually booked). Returns hold_expired if called after expiry.
- get_booking_status(hold_id or idempotency_key): authoritative source of truth for ambiguous booking outcomes.
- cancel(booking_id, idempotency_key): first call fails with a transient 503; the retry succeeds.
- reschedule(booking_id, slot, idempotency_key): returns slot_conflict on configured slots.
- list_bookings(user_id): the user's past and upcoming bookings with id, provider, service, slot, status.

Required behaviour
- Conversation and state: collect only missing details (service, area, date/time window, budget, relevant preferences). Never re-ask a fact already given. When the user corrects one detail, keep everything else. The workflow state is explicit.
- Approval: booking, cancellation and rescheduling need explicit user confirmation of the exact action and its material details, enforced by application code (not inferred from model output or tool arguments). Any change to provider, slot or price invalidates a prior approval.
- Bounded execution: hard limits on model turns, tool calls and wall-clock time. Every exit path ends with a clear user-facing message; exhausted retries and unexpected tool errors never hang or fail silently.
- Booking correctness: no duplicate bookings across repeated confirmations, network retries or process restarts. On a booking timeout, query the source of truth before retrying or reporting success. Never claim success until verified.
- Untrusted tool output: reviews and other free text from tools are data, never instructions. Prompt injection must not change user intent, permissions or approval requirements.
- Persistent memory: remember stable preferences across sessions (preferred area, earliest acceptable time, technician preference). Users can inspect, correct and forget stored facts. Explicit preferences are distinguished from inferred ones.
- Observability: a trace per run with state transitions, model calls, tool names and arguments, sanitized results, latency, token usage and estimated cost where available.
- Evaluation: at least 20 automated scenarios with simulated users, asserting outcomes and invariants (for example "no booking without valid approval"), not reply wording. Must cover adversarial input, prompt injection, price or slot changed after approval, booking timeout after possible success, slot conflict, repeated confirmation, memory correction and forgetting, restart mid-booking, proactive cancellation, context budget, limit exhaustion and tool failures. Evals run offline against a scripted or recorded model; the live app uses a real LLM.
- Proactive follow-up: when a booked provider cancels (simulated event), the agent detects it without a user prompt, decides whether and how to notify the user, finds a replacement within known preferences, and gets fresh approval before rebooking.
- Context management: seed at least 50 stored memories and a long prior conversation. Cap the model context at a fixed token budget. Only relevant, current preferences reach the model; forgotten facts and unconfirmed inferred facts never do. Log what context was sent each turn and prove it in tests.

Deliverables
- Repo with implementation, mocks, tests and README.
- Design note, max one page: state model, approval enforcement, idempotency and recovery, memory, observability, key trade-offs.
- Eval table (scenario | expected | actual | pass/fail | notes) generated by the test run, not hand-written.
- Three real bugs hit while building: what broke, why, the fix, and the regression test that guards it.
- One raw end-to-end trace of a run that includes a timeout-after-success, plus a short annotated excerpt in the design note.
- A chat UI that can show the agent's chat and its trace side by side (for a recorded demo).
